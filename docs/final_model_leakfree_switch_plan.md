# Plan 1 — 최종 모델 전환·확정 (exp41 → exp47, leak-free)

> 목적: 동반구매(장바구니) 엣지의 **target leakage**를 진단하고, leak-free 모델 `exp47_no_copurchase`를 새 최종 모델로 확정. 장바구니 데이터는 GNN 입력에서 빼되 **별도 product→product 인사이트 레이어로 재배치**(Plan 2에서 활용).
> 후속: 확정 후 [Plan 2 — EDA·MD 처방](eda_channel_prescription_plan.md)을 exp47 기준으로 수행.

---

## 0. 배경 — 왜 바꾸나

기존 최종 모델 `exp41_trend_kw3_ip1`(test PR-AUC 0.696)은 동반구매 엣지(`co_offline`/`co_quick`)를 학습에 포함. 그런데 이 엣지는 **신제품 출시 *이후*의 매출 행동**을 반영 → cold-start 성공예측에 **데이터 누수**.

프로젝트 목적은 **출시 전(cold-start) 신제품 키워드 조합 추천**이므로, 출시 후에만 존재하는 신호에 기댄 모델은 실력을 과대평가한다.

## 1. 누수 진단 증거 (실측)

| 지표 | 값 | 의미 |
|---|---|---|
| 동반구매 엣지 보유 제품 | 759 / 5,033 (15%) | |
| **성공 제품 보유율** | **46.1%** | |
| **실패 제품 보유율** | **5.4%** | 실패는 적게 팔려 동반구매 쌍 형성 불가 → **구조적 부재** |
| 성공 평균 동반구매 degree | 2.4 vs 실패 0.1 | 24배 |
| **동반구매 degree 단독 성공예측 PR-AUC** | **0.518** (base 0.238) | 모델 없이도 2.2배 |
| lift CSV 날짜 컬럼 | **없음** | 시간축 post-hoc 필터 불가 |
| lift pair 등장 제품 | **전부 NPD** (offline 681/681) | 출시 후 행동 불가피 |

> **누수의 본질**: 동반구매 쌍은 "출시 후 충분히 팔림"을 전제 → "엣지 보유 ≈ 성공"의 동어반복. `relation_importance`에서 `co_offline` α=0.131로 **모델이 가장 의존**하는 관계였음.
> **시간축 가드레일이 불가능한 이유**: 신제품은 출시 *이전* 동반구매 이력이 정의상 0. "출시 전 이력만" 필터 시 모든 NPD의 동반구매 신호가 사라짐 → 누수는 "고칠" 수 없고 **제거**해야 함.

## 2. exp47 vs exp41 비교

| 지표 | exp41 (동반구매 O) | exp47 (동반구매 X) |
|---|---|---|
| test PR-AUC | 0.696 | **0.570** |
| val PR-AUC | 0.729 | 0.578 |
| train PR-AUC | 0.753 | 0.793 |
| train-val gap | 0.024 | **0.215 (과적합↑)** |
| **운영점(predpos=23.8%) P=R=F1** | **0.668** | **0.666** |
| 운영 THR | 0.6647 | **0.7755** |
| 1위 관계 | co_offline 0.131 (출시 후) | **sim_kw 0.174 (기획시점 가용)** |
| 상위 관계군 | 동반구매 | sim_kw / sim_ip / 키워드 |

**핵심 해석**: PR-AUC는 0.696→0.570로 떨어지나 **우리가 실제로 쓸 운영점 성능은 0.668→0.666로 동일**. 차이는 전부 **랭킹 꼬리**(동반구매로 "초대박 확정" 제품을 최상위로 올린 부분)이며, 이는 cold-start에서 사용 불가한 신호. → **잃는 0.126은 실력이 아니라 증발하는 누수.**

## 3. exp47 leak-free 검증 (잔여 누수 점검)

exp47이 기대는 관계도 누수인지 degree-단독 예측력으로 점검:

| feature | degree 단독 PR-AUC | 성공 보유율 vs 실패 | 판정 |
|---|---|---|---|
| co_offline+co_quick | 0.518 | **46% vs 5%** | 🔴 구조적 누수 (제거 대상) |
| sim_kw | 0.393 | 98% vs 94% | 🟢 거의 전원 보유 → 내용 유사성 (기획시점 가용) |
| has_kw | 0.371 | 100% vs 100% | 🟢 전원 보유, 신호는 *어떤* 키워드 (=킬러/지뢰) |
| sim_ip | 0.295 | 29% vs 15% | 🟡 약한 내용 신호 |
| has_ip | 0.274 | 30% vs 17% | 🟡 약한 내용 신호 |

**판정**: 누수의 표식은 "실패 제품의 **구조적 부재**"(co_offline 5%). sim_kw/has_kw는 **94~100% 전원이 엣지 보유**, 신호가 degree·구성에 있음 = **출시 전 아는 내용 유사성** = 의도된 KGAT cold-start 메커니즘. → **exp47은 실질 leak-free, 0.570은 정직한 cold-start 천장.**

## 6. (선택) 과적합 완화 후속 — leak-free 그리드

exp47의 큰 train-val gap은 동반구매 지름길이 사라지자 키워드/IP에 과적합한 결과. 여유 시 **leak-free 조건 고정(동반구매 X) + 정규화 스윕**으로 더 나은 exp47 변형 탐색.
- **정규화 레버 상세는 §9-6 표 참조** (멀티태스크 λ 제외 — 그건 v2 전용). exp47 단독엔 dropout↑/weight_decay↑/hidden_dim↓/DropEdge 적용.
- 판정: val PR-AUC 최대 + gap 최소. 더 나은 게 나오면 그걸 최종으로 교체(Plan 2 재실행은 캐시만 재생성).
> ⚠ 이건 **선택 후속**. exp47로 Plan 2 착수해도 무방(운영점 성능 충분). v2(§9)로 갈 거면 §9-6에서 통합 처리.

## 7. 장바구니 데이터 재배치 (GNN 입력 → 인사이트 레이어)

**현황 진단**: `recommend.py`/`build_chain`은 `keyword→product→keyword`(has_kw)만 순회 → 장바구니 엣지를 **명시적으로 타지 않음**. 현재 장바구니의 유일한 기여는 분류기 메시지 패싱(=누수 지점)뿐, 의도한 product→product 인사이트는 **미실현 상태**.

**재배치 원칙**: 장바구니를 **분류기에서 빼고(exp47)**, raw co-purchase 쌍(`offline/quick_commerce_edge_lift_pair_out.csv`, Lift)을 **Plan 2의 별도 product→product 보완재 순회 레이어**로 승격.
- *"시드 제품 X ↔ 동반구매 {A,B}(Lift) → 그 제품들의 속성 = 보완 키워드"*
- **누수 없음**: X 자신의 성공 예측이 아니라 X와 함께 팔리는 *관계*를 보는 것 → 시간축 무관.
- → 의도한 도메인 인사이트를 **오히려 더 제대로 실현**(분류기에 묻혀 누수로만 쓰이던 것을 명시적 레이어로).
- (선택) `recommend.py` 순회에 product→product 홉을 옵션으로 확장.

## 9. Model v2 — 장바구니를 *누수 없이* 학습에 복원 (병렬 R&D 트랙)

> 동기: 동반구매(상품 궁합)는 제품의 내재 가치를 정의하는 핵심 정보. 배제 대신 **"입력 피처(누수)"를 "예측 타깃/구조(비누수)"로 전환**해 영향력을 학습에 녹인다.
> 위치: exp47(서빙)과 **독립 병렬**. v2가 §9-3 누수 하니스 통과 **AND** cold-start 운영점에서 exp47 초과 시 → 최종 교체.

### 9-1. 접근 2 — 멀티태스크 (co-purchase = 보조 link-prediction 타깃)
- **구조**: 공유 HGT/KGAT 임베딩 위에 두 헤드.
  - **주 헤드**: product 성공 로짓 (기존).
  - **보조 헤드**: product 쌍 임베딩 → 동반구매 링크 예측(이진 또는 Lift 회귀). 양성=co-purchase 쌍, 음성=랜덤 비-동반구매 쌍.
  - 손실 `L = BCE_main + λ·L_aux`.
- **누수 차단 핵심 (필수 조건)**: 보조 손실의 양성/음성 쌍은 **train-mask 제품에만** 한정. (co-purchase 라벨이 성공과 상관 46%v5% → test 제품 쌍이 transductive하게 임베딩을 빚으면 재누수.)
- **왜 비누수**: 추론 시 미래 영수증 입력 없음. 모델은 *content → 동반구매 잠재력*을 학습 → "이 속성은 장바구니 궁합이 좋겠다 → 잘 팔리겠다"는 적법한 forward 추론.
- **데이터**: 기존 co-purchase CSV(NPD)를 보조 타깃으로 그대로 사용 — **재채굴 불요.**

### 9-2. 접근 3 — 키워드-키워드 보완 엣지 (basket → keyword complementarity)
- **구성**: 제품 A·B가 동반구매(Lift≥thr)이면 A의 키워드 ka ↔ B의 키워드 kb에 보완 엣지. **여러 제품 쌍이 그 키워드 조합을 공유할 때만**(지지도 ≥ N) 생성 → 새 엣지타입 `keyword__basket_comp__keyword` (기존 `trend_to`와 별개).
- **왜 비누수(거의)**: 제품 단위가 아니라 **키워드 단위로 집계** → 특정 성공 제품 하나의 성공이 직접 인코딩 안 됨. 잔여 약누수(post-launch 기원)는 집계로 희석.
- **왜 목적 직결**: 최종 목적이 "키워드 *조합* 추천"인데, 보완 키워드 조합을 **그래프 구조로 직접 주입** → 추천 품질 향상.
- **데이터**: 기존 co-purchase CSV 집계 — 재채굴 불요.

### 9-3. 누수 재검증 (논증 아닌 측정 — 필수)
exp41을 잡은 건 measurement였음. v2도 동일 하니스 적용(= Plan 2 §9):
1. 도입 신호(aux/보완엣지) degree가 성공을 **구조적으로 예측하나** 재측정(degree 단독 PR-AUC, 보유율 성공vs실패).
2. aux를 **train-only로 건 게 맞는지** hold-out 검증 (test 임베딩 비오염).
3. 순열 귀무로 우연 아님 확인.
> "비누수일 것"은 가설. 통과해야 확정.

### 9-4. 승격 기준
- v2 §9-3 누수 하니스 **통과** **AND** cold-start 운영점(F1@THR) 에서 **exp47 초과** → 최종 교체 (Plan 2는 캐시만 재생성).
- 미달 시 exp47 유지, v2는 실험 기록(`experiments_master_log.md`)에만 남김.

### 9-5. (후순위) 접근 1 — legacy 매대 그래프
- ⚠ **현재 데이터에 legacy 동반구매 없음**(lift pair 전부 NPD) + legacy 제품 비-노드 → **B2(`거래번호`) 재채굴 + legacy 노드 추가** 필요.
- 신호 상당부분 `sim_kw`와 중복 → **ROI 낮음. 접근 2·3가 부족할 때만.**

### 9-6. 과적합 방지 — 정규화 스윕 (v2 필수)
> exp47의 train-val gap 0.215는 동반구매 지름길이 사라지자 키워드/IP에 과적합한 결과. v2는 멀티태스크 헤드로 **용량이 더 늘어** 정규화가 **선택 아닌 필수**. 동일 스윕은 exp47 단독(Plan §6)에도 적용 가능.

**레버 (현 config 기준값 → 조정):**
| 레버 | 현재 | 조정 | 효과 |
|---|---|---|---|
| `model.dropout` | 0.3 | **0.4~0.5** | HGT 어텐션·head 과적합 억제 |
| `train.weight_decay_w` | 0.0005 | **0.001~0.005** | W L2 규제 |
| `model.hidden_dim` | 64 | **48 / 32** | 용량↓ (메모: h=128 과적합·64 선택 → 더 낮춰 일반화) |
| **DropEdge** | 없음 | **0.1~0.3** | sim_kw 100만 dense 엣지 무작위 드롭 = GNN 정규화 |
| **aux λ (멀티태스크)** | — | **0.1~1.0 스윕** | 보조 task가 공유 임베딩에 inductive bias = **정규화 그 자체** |
| `early_stopping_patience` | 30 | 유지 | val_pr_auc 기준 best-val 체크포인트 |
| (선택) label smoothing / `pos_weight`(3.24) | — | 미세조정 | 불균형·과신 완화 |

- **핵심 통찰**: 멀티태스크 aux task(9-1)는 **그 자체가 강력한 정규화**. co-purchase 궁합을 동시에 맞춰야 하므로 공유 임베딩이 키워드 라벨에만 과적합하지 못함 → gap 자연 축소 기대.
- **판정**: **val PR-AUC 최대 + train-val gap 최소**(목표 gap < 0.10). train 성능을 희생해도 **val/test(진짜 cold-start)가 유일 기준**.
- **스윕 운영**: leak-free 조건 고정(동반구매 입력 X) + 위 레버 그리드. 기존 미사용 config(`exp44~46`)는 동반구매 포함이라 leak-free 기준 재구성 필요.
